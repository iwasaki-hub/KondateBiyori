# こんだて日和 — 画面構成・技術設計 v1.0

- 作成日: 2026-11-17
- 状態: 設計案（未実装）

## 1. 情報設計
```
起動
 ├ 初回設定（家族人数 / 苦手な食材 / 調理時間）
 └ タブ
    ├ 今週（デフォルト）
    │   ├ 週次作成条件 → 7日分を生成
    │   ├ 曜日カード → レシピ詳細
    │   ├ 曜日カード → 献立変更（候補/AI相談）
    │   ├ 過去週・翌週への切替
    │   └ プラン保存と状態確認
    ├ 買い物
    │   ├ カテゴリ別食材・必要量・購入済みチェック
    │   ├ 家にある食材の除外
    │   └ 手動編集/追加
    └ 設定
        ├ 家族プロフィール
        ├ プレミアム（将来の決済画面）
        ├ ログイン / 同期（提供時）
        ├ プライバシー / 利用規約
        └ データ削除 / アカウント削除（提供時）
```

## 2. 主要画面ごとの構成
### S01 初回プロフィール
- タイトル「あなたの家族に合わせて」
- 大人人数、子ども人数のステッパー、時短選択、苦手/除外食材のチップ、次へ
- 省略可能な入力はスキップ可能にする
- 成功: 家族人数が再起動後に残る

### S02 今週（ホーム）
- 上部: 「11/16〜11/22」週表示、前週/次週矢印
- 主ボタン: 「今週の献立を作る」/ 作成済みなら「もう一度提案」
- 7行: 月〜日、料理名、時間、タグ、右端「変更」
- 下部主動線: 「買い物リストを見る」
- 空状態: 「まだ献立がありません」+ 生成ボタン
- 生成中・失敗時: 状況説明と再試行、既存献立は保持

### S03 レシピ詳細
- 献立名、所要時間、人数、材料（単位・数量）、ステップ
- 手動で料理を差し替え
- 誤った材料があればユーザーが確認しながら編集できること

### S04 献立変更 / AI相談
- 「水曜は魚以外」「15分以内」「家にじゃがいもがある」などのクイックチップ
- 自由入力欄、変更候補カード、確定/取消
- 変更はプレビュー→確定。別曜日の内容は維持
- AIの回答は説明文として扱い、実際のデータはレシピIDで検証

### S05 買い物
- 上部: 対象週、未購入品の件数
- グループ: 野菜/肉・魚/卵・乳製品/乾物・調味料/その他
- 行: □ 食材名、数量・単位、手動修正メニュー
- 補助: 「家にある」マーク、「食材を追加」
- 合算不可の単位は別行で表現する

### S06 設定・マイページ
- 家族条件 / データ同期 / 利用プラン / ヘルプ / プライバシー / 利用規約 / データ削除
- 課金を開始したら、契約状態、購入復元、解約案内が見つけやすい位置にある

### S07 ペイウォール（3週目以降）
- 現在の無料枠とPremium特典、月額価格、請求周期、自動更新説明
- 購入、復元、利用規約、プライバシー、閉じる
- 実課金テストはdevelopment build / Sandboxで行う

## 3. デザイン原則
- 食卓を連想する温かなクリーム・深緑の落ち着いた色。主要操作は同じアクセント色
- 料理写真なしでも献立名が読みやすい。写真は必須にしない
- iPhone片手で使用しやすい下部タブ、44pt以上を目安に押しやすいタップ領域
- 重要操作（生成・確定・買い物）を目立たせ、ページごとに主要CTAは一つ
- Empty/loading/error/success/sync競合状態を定義

## 4. 推奨スタック
- UI: Expo SDK 58 + Expo Router + React Native + TypeScript
- ローカル: expo-sqlite（永続化、マイグレーション管理）。初期はローカル動作可能にする
- クラウド: 新規Supabaseプロジェクト（Auth、PostgreSQL、RLS、Edge Functions）
- AI: サーバーサイド呼び出し。APIのモデルとベンダーは設定で差し替え可能にする
- 決済: RevenueCat + App Store In-App Purchase（3週目以降）
- 検証: TypeScript、ESLint、Vitest/Jestの純粋関数テスト、iPhone実機、EAS preview
- GitHub: LittleDiaryとは独立した新規リポジトリ`KondateBiyori`を推奨

## 5. サーバーアーキテクチャ
```
Expo app
  ├ local db (profile / drafts / cached recipes / shopping checks)
  ├ Supabase Auth → JWT
  ├ Supabase PostgREST (RLS protected records)
  └ POST /generate-week | /replace-meal → Supabase Edge Function
      ├ auth検証 + rate limit + 利用上限チェック
      ├ 入力検証 + レシピ候補ID取得
      ├ AI service（シークレット鍵はEdge Functionsだけ）
      ├ 出力schema検証 + 除外食材の再検証
      └ 有効なrecipe_idのみ返す（失敗時は安全な候補/明示エラー）
```
注意: レシピ候補データの台帳化が重要。自由生成したテキストをそのまま料理・食材・アレルゲン情報の真実としてDBに確定しない。

## 6. 最小データモデル
- `recipes(id, title, time_minutes, servings_base, instructions_json, tags_json, is_active)`
- `ingredients(id, canonical_name, category, base_unit)`
- `recipe_ingredients(recipe_id, ingredient_id, quantity, unit)`
- `households(id, owner_user_id, adults, children, max_minutes, preferences_json, created_at)`
- `meal_plans(id, owner_user_id, household_id, week_start, status, created_at, updated_at)`
- `meal_plan_items(id, meal_plan_id, meal_date, recipe_id, servings, note)`
- `shopping_items(id, meal_plan_id, ingredient_id_nullable, label, quantity, unit, purchased, stocked, user_edited)`
- `ai_usage(id, owner_user_id, kind, period_key, idempotency_key, created_at)`（操作サーバー限定）
- 課金導入時: `entitlements(owner_user_id, provider, status, expires_at, updated_at)`（webhook同期、クライアント書込不可）

制約・検証:
- `meal_plan_items`は `(meal_plan_id, meal_date)` が一意、週の7日以外を登録できない検証
- `recipes`, `ingredients` は閲覧可能/更新権限を管理者またはサーバー限定
- `households`, `meal_plans`, `shopping_items` の所有者アクセスのみRLSで許可
- 所有者を他人に変更するUPDATEはUSING/WITH CHECKで拒否
- 利用者A/Bで読取/追加/変更/削除の権限制御テストを実施
- マイグレーションはGit管理。ローカル隔離環境で実行→stagingで検証→remote本番は人による承認後

## 7. 生成と買い物集計の仕様
- 初期レシピ台帳: 自作の定番夕食50件程度を目標。料理名、主食材、1人前の数量、作業手順を作成
- 週間生成: 7つの有効なrecipe_idを選ぶ。曜日固定条件、時間制限、除外食材を検査
- 世帯人数: 食数をプロファイル人数から算出。ただし子どもの量は一律に決めつけない（ユーザー補正）
- 数量合算: 食材名を正規化。g/kg、mL/Lなど明確に換算可能な単位のみ合算
- 在庫品: 購入対象から除くが、献立/必要量は保持
- AI生成失敗: 前回の確定した献立を消さない。ローカルの候補リストから提案できる

## 8. 公開前のセキュリティ/品質チェック
- APIキーがアプリバンドル/履歴/ログに入っていない
- Supabase RLSを実JWTでユーザーA/Bテスト
- 全体・ユーザー単位のAI呼出上限と費用アラート
- 冪等リクエスト、タイムアウト、再試行時の二重課金防止
- ゲスト利用からログイン移行時のデータ統合で勝手な上書きを防止
- 利用者が自分の情報を削除できる
- 料理・食品のアレルギーについて誤った安全保証表現を使わない
- UI/モデル負荷/通信失敗の実機確認
