# こんだて日和 — 最初の14日間の開発計画 v1.0

- 作成日: 2026-11-17
- 想定: 1日1PR、各PRは単一責務。スケジュールは目安（審査/外部認証/開発時間により変動）。
- リポジトリは新規独立 `iwasaki-hub/KondateBiyori` を推奨（**未作成**）。既存LittleDiaryには変更を加えない。
- 基本: `feature/<issue>` → PR → CI pass → iPhone必要箇所の手動確認 → squash merge。
- Day 1.5導入後のPRレビューでは、CIに加えてVercel Previewのビルド・表示・アセット読込・エラーを確認し、必要箇所はiPhone Safariでも目視する。
- 初期14日で「非課金のテスト版MVP」を目標とする。正式課金・ストア公開は後工程。

## 安全な作業ルール
- 原則 `main` に直接pushしない。各PR開始前にmain更新と作業ツリーcleanを確認
- 機密情報、`.env.local`、APIのservice_role/secret鍵のコミット禁止
- PR説明には目的、変更ファイル、テスト結果、スクリーンショット、ロールバック方法
- DB/認証/課金はPRがmergeされたことと本番操作を分ける。共有/本番資源への破壊的変更は事前承認
- Supabase migrationの `db reset`/`db push` は対象DBを必ず確認、既存のLittleDiary DBは触れない
- CIは`typecheck`/`lint`/`test`を必須。バージョンは互換性を確認して固定
- 1 PRが大きすぎる場合はサブPRへ分けて日数を繰り延べる

## 14日間 / 14PR

以下の「PR #1〜#14」は当初の計画上の番号であり、GitHubの実際のPR番号とは一致しない。Day 1の実PRは #2。追加工程Day 1.5を挿入し、既存Day 1〜14の日程・仕様・計画番号は保持する。

### Day 1 — PR #1: 新規リポジトリとExpo起動
**実装**: Expo SDK 58 + TypeScript + Expo Router、README、`.gitignore`、`.env.example`、初期画面、AGENTS.md。
**受け入れ条件**: iPhone Expo Goまたは開発環境で起動、`tsc --noEmit`成功、ESLint成功、秘密情報0件。LittleDiaryに変更なし。

### Day 1.5 — 追加工程: Vercel Web Preview導入
**実装**: Expo SDK 58とWeb static出力を維持し、VercelをFramework Other、Root Directory `.`、Install `npm ci`、Build `npm run build:web`、Output `dist`で構成。`.vercel/`を除外し、READMEにGit連携・検証手順を記載する。SPA用一括rewriteや不要な依存を追加しない。
**受け入れ条件**: `npm ci`、`npm test`、Expo Doctor、Webビルド成功。distのHTML・アセットとVercel設定の構文を確認。まずPR #2を取り込んだmainからProductionを公開しHTTP 200を確認する（2026-11-17に利用者が外部公開を承認済み）。次にPR #3のPreviewでビルド、HTTPアクセス、アプリ名、JS/CSS読込、404・重大なブラウザエラーを検証。iPhone Safariは利用者が目視確認。Preview確認後にPR #3をマージしてmainのProductionが自動更新されることを確認する。mainの自動デプロイを無効にしない。有料プラン変更は別承認。実際のPR番号とデプロイURLはPRで管理する。

### Day 2 — PR #2: UIデザイントークンとタブ
**実装**: 色/タイポ/余白のトークン、共通Button/Card、今週・買い物・設定の3タブ。
**受け入れ条件**: 3タブを移動可能、狭いiPhone画面でも横スクロール不要、アクセシビリティラベルあり。

### Day 3 — PR #3: レシピ台帳とスキーマ
**実装**: `Recipe`, `Ingredient`, `MealPlan` 型、初期10件の権利確認済み自作サンプル（50件への拡充は後続）、バリデータ。
**受け入れ条件**: 存在しないrecipe_idを拒否、各レシピに材料・分量・手順が存在、単位検証テスト合格。

### Day 4 — PR #4: 家族プロフィール画面
**実装**: 人数、時間、苦手食材、任意の除外食材、入力検証。
**受け入れ条件**: 必須入力/任意スキップ正常、変更値がローカル保存・再起動後復元、入力が不正ならエラー表示。

### Day 5 — PR #5: 週間献立の表示
**実装**: 指定週の7日表示、前週/次週、空状態、サンプルプラン生成（AIなし）。
**受け入れ条件**: 月〜日が1回ずつ、週の境界をまたいでも日付正しい、空/読み込み状態あり。

### Day 6 — PR #6: レシピ詳細と人数別分量
**実装**: 料理名・時間・手順・材料の詳細画面、食数調整。
**受け入れ条件**: 詳細を開閉でき、人数変更で材料分量の計算が正しい。少数・単位のテストあり。

### Day 7 — PR #7: 1日分の献立差し替え
**実装**: 候補リストから任意の曜日を差し替える確認画面。
**受け入れ条件**: 選択した1日だけ更新、他6日不変、取消時は変更なし、テスト付き。

### Day 8 — PR #8: 買い物リスト集計ロジック
**実装**: 曜日ごとの材料から同一食材を集計、カテゴリ表示。
**受け入れ条件**: g/kg・mL/Lの合算テスト合格、個とgの混合を誤合算しない、差し替え時に再計算。

### Day 9 — PR #9: 買い物リスト操作と保存
**実装**: 購入済みチェック、在庫品除外、手動追加/編集、ローカル永続化。
**受け入れ条件**: アプリ再起動後も状態復元、プラン更新後は手動追加分を意図せず消去しない、UI操作の実機確認。

### Day 10 — PR #10: 新規Supabaseの接続基盤
**実装**: プロジェクト設定、公開可能キーの設定、Authクライアント、ログイン/ログアウト導線。新規環境に限定。
**受け入れ条件**: CIに秘密鍵なし、ログイン失敗が安全に表示、ゲスト基本機能が動く。外部プロジェクト作成は明示承認。

### Day 11 — PR #11: DBマイグレーション・RLS
**実装**: 家族、献立、日別レコード等のSQL、所有者限定RLS、テスト計画。
**受け入れ条件**: 隔離DBで適用・再適用/差分確認、ユーザーA/Bの越境CRUD拒否、anon非公開確認。本番適用は別承認。

### Day 12 — PR #12: AI用Edge Function
**実装**: 構造化出力schema、認証、入力検証、上限、ログの最小化、失敗時の代替提案。
**受け入れ条件**: 無認証・上限超過・不正recipe_idを拒否、鍵はサーバーのみ、モック試験合格。実課金API連携は承認後。

### Day 13 — PR #13: AI週間生成と1日変更の接続
**実装**: 画面→Edge Function→レシピID照合→保存。AI会話導線、エラーリトライ。
**受け入れ条件**: 7日生成、1日変更、他6日保持、AI失敗時も保存済みデータは保持。通信切断テスト。

### Day 14 — PR #14: ベータ品質チェック
**実装**: エラーメッセージ/空状態/UX修正、テスター用README、EAS preview（環境が許す場合）。
**受け入れ条件**: タイプチェック・lint・ユニットテスト全成功。iPhoneで初回設定→生成→変更→買い物→再起動を完走。重大バグ0、既知問題一覧化。

## 収益シミュレーション（仮定）
- 月額480円 × 有料会員160人 = 売上76,800円/月
- アプリ内決済総手数料15%という条件を仮定: 手数料11,520円
- AI/インフラ変動費60円 × 160人 = 9,600円
- その他固定費 5,000円/月を仮置き
- 残額50,680円/月（税・追加費用・開発者労働対価控除前）
- 従って月5万円は『会員160人で確実』ではなく、単価・継続率・実原価に依存する目標値
